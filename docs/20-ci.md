# CI と掲示

入口はひとつ。ローカルでも CI でも同じものを実行する。

```sh
make verify      # ./run.sh + 集計。結果は .work/report/ に残る
```

`make verify` が行うのは次の3つである。CI はこれに「掲示用の枝への押し込み」を足すだけで、
検査の内容そのものはローカルと変わらない。

| | 生成物 |
|---|---|
| 検査を走らせる（`./run.sh`） | `.work/results.tsv` `.work/projects.tsv` `.work/packages.tsv` `.work/meta.tsv` |
| 1回分をまとめる（`report.py run`） | `.work/report/summary.md` `.work/report/results.json` |
| 履歴から表と図を描く（`report.py site`） | `.work/report/index.html` `.work/report/history.svg` `.work/report/history-dark.svg` |

## 1. 準備

**設定する秘密はひとつも無い。**

本スイートは dowel の成果物を必要とする。dowel は別リポジトリだが公開されている
ため、`actions/checkout` は既定の `GITHUB_TOKEN` のまま読める。`GITHUB_TOKEN` は
本リポジトリを対象とする installation token であり他リポジトリへの権限を持たないが、
公開リポジトリの読み取りに権限は要らない。

```yaml
      - uses: actions/checkout@...
        with:
          repository: sabas0ba/dowel
          ref: ${{ env.DOWEL_REF }}
          # token も ssh-key も渡さない
```

### dowel が非公開に戻った場合

そのときは資格情報が要る。**取り出し方を変えても回避できない**。認証を要求して
いるのは経路（clone / fetch / tarball / release 資産）ではなく、リポジトリが
非公開であることそのものであり、どの経路も同じ認証を通る。

採りうる形は以下。かつて本ワークフローはデプロイキーを用いていた（`9fc36cd`）。

| 形 | 資格情報 | 備考 |
|---|---|---|
| 読み取り専用のデプロイキー | 秘密鍵1つ | 対象が構造上1リポジトリに固定され、利用者アカウントにも紐づかない。最も狭い |
| GitHub App の installation token | App ID + 秘密鍵 | 1時間で失効する点は優れるが、設定する秘密が増える |
| 個人アクセストークン | トークン1つ | 対象を後から広げられ、期限切れのたびに差し替えが要る。採らない |

デプロイキーに戻す場合は、`sabas0ba/dowel` の Deploy keys に公開鍵を
（**write は付けずに**）登録し、秘密鍵を `DOWEL_DEPLOY_KEY` として本リポジトリの
Actions secrets に置き、checkout に `ssh-key: ${{ secrets.DOWEL_DEPLOY_KEY }}` を
足す。あわせて、鍵が無いまま進まないよう checkout の前に番人を戻すこと。
非公開リポジトリに対する認証の失敗は 404 として返るため、そのままでは
「リポジトリが存在しない」と読める誤りになる。

### 掲示用の枝

`gh-pages` を用意する必要は無い。無ければ CI が作る。

作り直したい場合は枝を消せばよい。次の実行で作り直される（履歴は失われる）。

### GitHub Pages として配信する

本リポジトリは公開されているため、追加の費用なく配信できる。

Settings → Pages → Build and deployment → Source を **Deploy from a branch**、
Branch を **`gh-pages` / `(root)`** にする。配信先は次のとおり。

```
https://sabas0ba.github.io/dowel_examples/
```

配信しない場合でも、表は枝の中の `index.html` として残り、GitHub 上で
ファイルとして読める。履歴の実体は `history.json` である。

### dowel の作業木が要ること

`09-acquisition` は `dowelup` を検査する。`dowelup` は取得をソースからの
ビルドとして行うため（ADR-0013）、検査には**上流にあたる git リポジトリ**が要る。

実際の上流には触れない。`run.sh` が見つけた作業木を手元へ bare 複製し、
`DOWELUP_UPSTREAM` でそちらを向ける。ネットワークにも上流の状態にも
左右されずに走る。

CI では checkout した `.dowel-src` がそのまま使える。追加の設定は要らない。
`dowelup` は `cargo build --release` が dowel と一緒に作る。

手元では `DOWELUP` と `DOWEL_SRC` で明示できる。既定では `dowel` の隣と
`../dowel` を探す。見つからなければ `run.sh` は始めない。環境によって
走る検査が変わると、結果を過去の実行と比べられなくなる。

## 2. どの dowel に対して走らせるか

版は `dowel-ref` に固定してある。

```
f65fe20a974f589a8ae424bf97d50010fb7745e2
```

枝の名前ではなくコミットを書く。枝を指すと、本リポジトリを何も変えていないのに
結果が動く。ある日の赤が、こちらの退行なのか本体の変更なのかを区別できなくなる。
「外側から検査する」という立場は、検査する対象が特定できて初めて成り立つ。

追随は、この1行を書き換える pull request として現れる。差分が「どの版へ移ったか」
そのものになり、そのとき `xfail` が `xpass` へ変わったかどうかも同じ実行で分かる。
本体の修正が本スイートに届いた瞬間が、履歴に1行として残る。

手元で同じ版を使う場合。

```sh
git -C ../dowel checkout $(grep -v '^#' dowel-ref | tail -1)
cargo build --release --manifest-path ../dowel/Cargo.toml
```

`0.1.0` からは、その版に release タグが付いている。**Rust の道具立てを
持たない機械でも、公開された資産から入れられる。**

```sh
dowelup install 0.1.0     # 公開バイナリを取り、隣の .sha256 と突き合わせる
```

固定に書くのは引き続き sha である。タグは動かしうるのに対し、コミットは
動かない——`dowel-ref` が答えるのは「どの版で検証したか」であり、
その問いにタグは答えられない。

## 2.5 公開された release を確かめる側

`verify` は上流の release に触れない。触れると、本リポジトリを何も変えて
いないのに、上流の資産が差し替わった日に結果が動く——`dowel-ref` を固定する
のと同じ理由である。

一方で、**公開された資産がその形で置かれているかは、そこでしか確かめられ
ない**。release は人が作る手順の産物であり、壊れ方も人の手順の壊れ方をする
——資産が1つ欠ける、digest を貼り忘れる、書庫の中身が変わる。どれも公開した
あとに気づくものである。

そこで別の workflow（`release.yml`）に分けてある。

| | `verify` | `release` |
|---|---|---|
| 相手 | `dowel-ref` の1行が指す版 | 上流に公開された release |
| 引き金 | 押し込みと pull request | 手動と日に一度 |
| 落ちたとき止まるもの | pull request | 何も止まらない（相手が外に在る） |
| 入れるもの | 検査に要る道具一式 | **`gcc` と `ninja` だけ** |

最後の行が要点である。Rust の道具立てを要らなくするのがこの配り方の目的
なので、確かめる側が rust を持っていては確かめたことにならない。

手元でも同じものが走る。

```sh
./scripts/check-release.sh 0.1.0
```

## 3. いつ走るか

| 引き金 | 検査 | 掲示 |
|---|---|---|
| `main` への押し込み | 走る | **押し込む** |
| pull request | 走る | 押し込まない |
| 手動実行（`workflow_dispatch`） | 走る | **押し込む** |

pull request で掲示しないのは、まだ入っていない変更の結果が履歴に混ざるのを避けるため。
pull request の結果はジョブ要約と成果物で見る。

手動実行では `dowel_ref` を渡せる。dowel 側の枝に対して本スイートを当てられる。

```
Actions → verify → Run workflow → dowel_ref: claude/fix-suggestion-span
```

本体の修正が本スイートの `xfail` を `xpass` に変えるかどうかを、
取り込む前に確かめられる。

## 4. 結果の見え方

結果は3か所に出る。用途が異なる。

### ジョブ要約

直近の実行だけを見る。プロジェクトごとの内訳、`Needs attention`、
`Known unfixed issues`、`Environment` が並ぶ。

### 成果物（Artifacts）

`summary.md` / `results.json` / `index.html` と、元になった TSV。
30 日保持する。失敗した実行の結果こそ残す価値がある。

### 掲示用の枝

節は5つ。

| 節 | 中身 |
|---|---|
| `Latest run` | 直近の実行のプロジェクト別の数。名前は実体のディレクトリへのリンク |
| `Checks` | **検査の全件**。プロジェクトごとに折り畳んであり、README と各パッケージへのリンクを添える |
| `Needs attention` | `fail` と `xpass`。無ければ出ない |
| `Growth` | 履歴の図。`History` と同じ数を絵にしたもの |
| `History` | 過去 100 回分。`passed / failed / known / fixed` を横に並べる |

見出しの直下に、検証対象（dowel のその版のコミット）、本リポジトリ、
`dowel-ref`、`docs/10-findings.md` への道を置く。掲示は結果しか持たないため、
「この検査は何を見ているのか」を追うには実体へ辿れる必要がある。

`Checks` は落ちているもの（`failed` / `known`）を含むプロジェクトだけ
開いた状態で出す。全部開くと読む前に諦める長さになる。

`History` で見たいのは各回の合否ではなく、**列の動き**である。

- `known` の数が減る → 本体が直った
- `fixed`（`xpass`）が 0 でなくなる → 直ったので宣言を外す番
- `passed` の数が増える → 検査を足した
- `failed` が出る → 退行

#### 図

その列の動きは、100 行の数字を上から下へ辿る限り読めない。`Growth` は同じ数を
1枚の図にする。3段からなる。

| 段 | 中身 |
|---|---|
| 総数 | 系統（`projects/` `apps/` `docs`）ごとに積んだ面。上端が総数そのもの |
| 未修正 | `xfail` / `fail` / `xpass` の推移。上の「列の動き」がそのまま線になる |
| 層ごと | 1層1枚の小さい面。縦軸を共有するため、現れた時期と大きさの双方が読める |

層は 27 あり、色で見分けられる数（7つ）を超えている。積み上げの色は系統3つに
だけ使い、層ごとの内訳は面を並べて示す。色数を増やして解こうとすると、どの色も
見分けられなくなる。

明暗2枚を書き出す。掲示の頁も README も両方の背景で読まれるため、片方を機械的に
反転させるのではなく、それぞれの背景に対して選んだ色を使う。色は実際に塗られる
濃さ（背景と混ざったあとの値）で検証してある（`scripts/chart.py` 冒頭）。

図は表の代わりではない。図が示す数はすべて `History` に全件並ぶ。

#### 枝に置くファイル

| ファイル | 中身 |
|---|---|
| `index.html` | 表と図の描画。`history.json` と `latest.json` から作る |
| `history.svg` | 図（明るい背景）。README がこの名前で参照する |
| `history-dark.svg` | 図（暗い背景） |
| `history.json` | 過去 100 回分。**各回の数だけ**を持つ |
| `latest.json` | 直近の実行の全件（検査1件ずつ、パッケージの一覧を含む） |

README はこの2枚を掲示用の枝の raw URL として埋める。したがって、**最初の
掲示が行われるまで README の図は表示されない**（枝を作り直した場合も同じ）。
名前が片方だけ変わると画像が静かに壊れるため、README の参照と
`scripts/chart.py` が書き出す名前が一致することは `docs` の段で検査する。

履歴に全件を積まないのは大きさのためである。検査を 100 回分すべて抱えると
読むにも押し込むにも重くなる。内訳が要るのは直近の実行だけなので、
そちらは `latest.json` に置き、`report.py site --latest` がそこから描く。

## 5. 合否の決め方

`fail` と `xpass` のどちらか1件でもあれば失敗とする。

`xfail` は失敗として数えない。本体の未修正事項に対する検査であり、
落ちていることが現況の記録だからである（`docs/00-design.md` 5節）。

`xpass` を失敗として扱うのは、**直ったことを見落とさないため**である。
本体が直ったのに宣言を外し忘れると、その検査は以後ずっと
「落ちていることになっているが実は通る」状態になり、記録として嘘になる。

## 6. 構成

| ファイル | 役割 |
|---|---|
| `.github/workflows/verify.yml` | 引き金と段取り。検査の中身は持たない |
| `run.sh` | 検査を走らせる。CI を知らない |
| `scripts/report.py` | 集計と描画。`run` / `append` / `site` の3つ |
| `scripts/chart.py` | 履歴から図を描く。`report.py site` が呼ぶ。単体でも走る |
| `.work/packages.tsv` | プロジェクトが含むパッケージ。掲示から実体へ辿る材料 |
| `scripts/check-docs.py` | 文書と実体の整合。`run.sh` の `docs` の段 |
| `scripts/publish-pages.sh` | 掲示用の枝への押し込み |
| `scripts/check-release.sh` | 公開された release を利用者と同じ経路で確かめる。`run.sh` の外 |
| `dowel-ref` | 検証に用いる dowel の版（コミット1行） |
| `lib/lsp_client.py` | `dowel lsp` と話すクライアント。`08-lsp` が使う |
| `Makefile` | ローカルの入口 |

`run.sh` が CI を知らないことは意図した分離である。CI で起きた失敗は、
必ず手元で同じ手順により再現できる。

外部アクションはコミットへ固定する（dowel 本体の `docs/50-development.md` 5節に合わせる）。
更新する場合は `git ls-remote --tags <repo>` でタグの指すコミットを確かめてから書き換える。

`publish-pages.sh` は `PAGES_REMOTE` で押し込み先を差し替えられる。
手元の bare リポジトリを相手に、枝の作成・追記・競合時の積み直しを確かめられる。

```sh
git init --bare /tmp/pages.git
GITHUB_RUN_ID=1 PAGES_REMOTE=/tmp/pages.git \
    ./scripts/publish-pages.sh gh-pages .work/report/results.json
```

## 7. 押し込みの競合

掲示用の枝への押し込みが競合した場合、履歴を取り直してから積み直す（3回まで）。
掲示の内容は「取り直した履歴 + 今回の結果」であり、他の実行の記録を捨てない。

同じ実行の再実行（`run_id` と `run_attempt` が同じ）は履歴を置き換える。
再実行しても行は増えない。
