# CI と掲示

入口はひとつ。ローカルでも CI でも同じものを実行する。

```sh
make verify      # ./run.sh + 集計。結果は .work/report/ に残る
```

`make verify` が行うのは次の3つである。CI はこれに「掲示用の枝への押し込み」を足すだけで、
検査の内容そのものはローカルと変わらない。

| | 生成物 |
|---|---|
| 検査を走らせる（`./run.sh`） | `.work/results.tsv` `.work/projects.tsv` `.work/meta.tsv` |
| 1回分をまとめる（`report.py run`） | `.work/report/summary.md` `.work/report/results.json` |
| 履歴から表を描く（`report.py site`） | `.work/report/index.html` |

## 1. 準備

### `DOWEL_DEPLOY_KEY`

本スイートは dowel の成果物を必要とする。dowel は別リポジトリかつ**非公開**であり、
`GITHUB_TOKEN` は本リポジトリだけを対象とする installation token であるため、
これでは取り出せない。何らかの資格情報が要る。

> **「特定の版を fetch すれば要らないのでは」は成立しない。** 認証を要求しているのは
> 取り出し方（clone / fetch / tarball / release 資産）ではなく、リポジトリが
> 非公開であることそのものである。どの経路でも同じ認証を通る。
> 資格情報を無くせる方法は「dowel を公開する」以外に無い。

用いるのは**読み取り専用のデプロイキー**である。個人アクセストークンは用いない。

1. 鍵を作る。パスフレーズは付けない（CI が使うため）

   ```sh
   ssh-keygen -t ed25519 -N '' -C 'dowel_examples CI (read-only)' -f dowel-ci
   ```

2. `sabas0ba/dowel` の Settings → Deploy keys → Add deploy key に
   **`dowel-ci.pub` の中身**を貼る。**Allow write access は付けない**
3. 本リポジトリの Settings → Secrets and variables → Actions に、
   **`dowel-ci`（秘密鍵の方）の中身**を **`DOWEL_DEPLOY_KEY`** として登録する
4. 手元の鍵ファイルは消す

   ```sh
   rm dowel-ci dowel-ci.pub
   ```

設定されていない場合、ワークフローは checkout へ進む前に理由を出して落ちる。
非公開リポジトリに対する認証の失敗は 404 として返るため、そのまま進むと
「リポジトリが存在しない」と読める誤りになるからである。

#### なぜデプロイキーか

| | 個人アクセストークン | デプロイキー |
|---|---|---|
| 対象範囲 | 発行時に選んだリポジトリ（後から広げられる） | **その1リポジトリに構造上固定** |
| 持ち主 | 利用者アカウント。その人の権限に紐づく | リポジトリ。誰にも紐づかない |
| 権限 | Contents: Read などを選ぶ | 読み取りのみ（write を付けなければ） |
| 失効 | 期限切れのたびに差し替え、その間 CI が赤 | 鍵を消すまで有効 |
| 漏れたとき | そのトークンが持つ全リポジトリ | dowel の読み取りのみ |

対象を後から広げられないこと、利用者アカウントに紐づかないことの2点が効く。

#### 他に採りうる形

| 形 | 資格情報 | 判断 |
|---|---|---|
| デプロイキー（採用） | 秘密鍵1つ | 対象が構造上1リポジトリに固定される。最も狭い |
| GitHub App の installation token | App ID + 秘密鍵の2つ | 1時間で失効する点は優れるが、設定する秘密が増える。組織で複数リポジトリを跨ぐようになったら移る価値がある |
| dowel を公開する | **不要** | 資格情報を完全に無くせる唯一の形。公開してよくなった時点で、このワークフローから `ssh-key` の行を消すだけで済む |
| 成果物を本リポジトリに置く | 不要 | バイナリを git に入れることになる。採らない |

### 掲示用の枝

`gh-pages` を用意する必要は無い。無ければ CI が作る。

作り直したい場合は枝を消せばよい。次の実行で作り直される（履歴は失われる）。

> **GitHub Pages として配信する場合。** 非公開リポジトリで Pages を配信するには
> 有料の計画が要る。配信しない場合でも、表は枝の中の `index.html` として残り、
> GitHub 上でファイルとして読める。履歴の実体は `history.json` である。

## 2. どの dowel に対して走らせるか

版は `dowel-ref` に固定してある。

```
a8a59e7c70aa3bd15f01d8c04cf7e38a00b3bd4f
```

枝の名前ではなくコミットを書く。枝を指すと、本リポジトリを何も変えていないのに
結果が動く。ある日の赤が、こちらの退行なのか本体の変更なのかを区別できなくなる。
「外側から検査する」という立場は、検査する対象が特定できて初めて成り立つ。

追随は、この1行を書き換える pull request として現れる。差分が「どの版へ移ったか」
そのものになり、そのとき `xfail` が `xpass` へ変わったかどうかも同じ実行で分かる。
本体の修正が本スイートに届いた瞬間が、履歴に1行として残る。

手元で同じ版を使う場合。

```sh
git -C ../dowel checkout $(grep -v '^#' dowel-ref | tail -1)
cargo build --release --manifest-path ../dowel/Cargo.toml
```

## 3. いつ走るか

| 引き金 | 検査 | 掲示 |
|---|---|---|
| `main` への押し込み | 走る | **押し込む** |
| pull request | 走る | 押し込まない |
| 手動実行（`workflow_dispatch`） | 走る | **押し込む** |

pull request で掲示しないのは、まだ入っていない変更の結果が履歴に混ざるのを避けるため。
pull request の結果はジョブ要約と成果物で見る。

手動実行では `dowel_ref` を渡せる。dowel 側の枝に対して本スイートを当てられる。

```
Actions → verify → Run workflow → dowel_ref: claude/fix-suggestion-span
```

本体の修正が本スイートの `xfail` を `xpass` に変えるかどうかを、
取り込む前に確かめられる。

## 4. 結果の見え方

結果は3か所に出る。用途が異なる。

### ジョブ要約

直近の実行だけを見る。プロジェクトごとの内訳、「直すべきもの」、
「既知の未修正事項」、実行環境が並ぶ。

### 成果物（Artifacts）

`summary.md` / `results.json` / `index.html` と、元になった TSV。
30 日保持する。失敗した実行の結果こそ残す価値がある。

### 掲示用の枝

過去 100 回分の履歴を積んだ表。プロジェクトごとの内訳を
「成功 / 失敗 / 既知の未修正 / 修正済み」の形で横に並べる。

見たいのは各回の合否ではなく、**列の動き**である。

- 既知の未修正の数が減る → 本体が直った
- 修正済み（`xpass`）が 0 でなくなる → 直ったので宣言を外す番
- 成功の数が増える → 検査を足した
- 失敗が出る → 退行

## 5. 合否の決め方

`fail` と `xpass` のどちらか1件でもあれば失敗とする。

`xfail` は失敗として数えない。本体の未修正事項に対する検査であり、
落ちていることが現況の記録だからである（`docs/00-design.md` 5節）。

`xpass` を失敗として扱うのは、**直ったことを見落とさないため**である。
本体が直ったのに宣言を外し忘れると、その検査は以後ずっと
「落ちていることになっているが実は通る」状態になり、記録として嘘になる。

## 6. 構成

| ファイル | 役割 |
|---|---|
| `.github/workflows/verify.yml` | 引き金と段取り。検査の中身は持たない |
| `run.sh` | 検査を走らせる。CI を知らない |
| `scripts/report.py` | 集計と描画。`run` / `append` / `site` の3つ |
| `scripts/publish-pages.sh` | 掲示用の枝への押し込み |
| `dowel-ref` | 検証に用いる dowel の版（コミット1行） |
| `Makefile` | ローカルの入口 |

`run.sh` が CI を知らないことは意図した分離である。CI で起きた失敗は、
必ず手元で同じ手順により再現できる。

外部アクションはコミットへ固定する（dowel 本体の `docs/50-development.md` 5節に合わせる）。
更新する場合は `git ls-remote --tags <repo>` でタグの指すコミットを確かめてから書き換える。

`publish-pages.sh` は `PAGES_REMOTE` で押し込み先を差し替えられる。
手元の bare リポジトリを相手に、枝の作成・追記・競合時の積み直しを確かめられる。

```sh
git init --bare /tmp/pages.git
GITHUB_RUN_ID=1 PAGES_REMOTE=/tmp/pages.git \
    ./scripts/publish-pages.sh gh-pages .work/report/results.json
```

## 7. 押し込みの競合

掲示用の枝への押し込みが競合した場合、履歴を取り直してから積み直す（3回まで）。
掲示の内容は「取り直した履歴 + 今回の結果」であり、他の実行の記録を捨てない。

同じ実行の再実行（`run_id` と `run_attempt` が同じ）は履歴を置き換える。
再実行しても行は増えない。
