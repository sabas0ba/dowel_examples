# スイートの設計

## 1. 立場

dowel 本体の検証（`docs/51-testing.md`）は層ごとに責務を割り当て、
同じ対象を複数の層で検査しないという方針を採っている。本スイートは
その層の外側にもう1枚を足すものであり、責務は次の1点に限る。

> **本体のソースを参照せず、公開されたコマンドと診断コードだけを使って、
> 利用者と同じ立場から確かめる。**

この制約には意味がある。本体の内側から書いたテストは、実装が持っている
前提をそのまま期待値にしてしまう。実装が仕様から外れていても、
テストは実装に合わせて書かれるため通ってしまう。外から書けば、
期待値の出所は仕様と文書しかない。

したがって本スイートの検査が落ちたとき、直すべき対象は3つのいずれかである。

1. 実装（仕様どおりでない）
2. 文書（仕様が実装と食い違っている、または曖昧である）
3. 本スイート（期待値の読み違い）

3 でないことを確かめてから、1 か 2 として本体へ報告する。
記録は [10-findings.md](10-findings.md) にある。

## 2. 何を重ならせないか

本体の `tests/projects/` と重複させない。あちらが固定するのは
「実プロジェクトの依存形状でのみ発現する性質」（3層以上、ダイヤモンド、
`include/` の相対パス衝突）である。本スイートが見るのはそれ以外、
すなわち構成の語彙・機能フラグ・診断・CLI の約束である。

`examples/hello` とも重複させない。あちらは文書に載せる最小の例であり、
壊れたときに直す対象は文書である。

## 3. 検査の置き場所

| 確かめたいこと | 書く場所 |
|---|---|
| 意味論（伝播する／しない、定義が届く） | C 側の `#error` と終了状態 |
| 実行結果 | `prints` で標準出力を完全一致で見る |
| 伝播しないこと、引数の中身 | `args_lack` / `args_have`（アクショングラフ） |
| 診断が届くこと | `diag`（`--message-format=json`） |
| 診断の中身（位置・注記・提案） | `diag_where` |
| 再ビルドで何が走らないか | `runs_actions`（direct 実行器の計数） |
| 再ビルドで走ったものの識別 | `rebuilt` / `not_rebuilt` |
| 文書と実体の整合 | `scripts/check-docs.py`（`docs` の段） |
| 壊れた入力に対する応答の形 | `07-robustness` の `probe`。1回の実行から4つの性質を判定する |
| 別の入口が同じ答を返すか | `08-lsp` の `agreement`。`dowel check` と `dowel lsp` に同じ本文を渡す |
| 版の選択 | `09-acquisition`。上流を手元の bare リポジトリに差し替える |
| どのコンパイラが翻訳したか | `10-toolchain`。C 側の `__clang__` / `__GNUC__` を成果物に名乗らせる |
| どのアーキテクチャ向けか | `11-cross`。C 側の `__aarch64__` とポインタ幅。qemu-user で実行まで通す |
| プロセスを跨いだ引き継ぎ | `12-store`。`--log-level=debug` の要約と `trace` の判定を数で見る |
| 同時に走ったかどうか | `13-parallel`。テスト自身に印を置かせる。壁時計の閾値を使わない |
| 増分の費用が木の大きさに比例しないこと | `14-scale`。走らせた数と**飛ばした数**の両方を見る |
| どの言語として翻訳されたか | `15-cpp`。C 側の `__cplusplus` と、リンクの driver |
| 移行で何が写り何が落ちたか | `16-migrate`。本物の CMake から取り込み、`migrate verify` で答合わせをする |
| 環境が決める依存の扱い | `17-deps`。`.pc` を持ち込んで pkg-config に引かせる。実際のシステムには触れない |
| 道具の宣言が本当に届いたか | `18-tools`。`graph --kind=action` のコマンド先頭と、出来上がった archive の中身 |
| 変換が本当に走ったか | `19-artifacts`。出来上がったファイルの中身（ELF の魔法数、ソースに埋めた印） |
| 1本の実行ファイルが複数の検査になること | `20-cases`。ラベルの文法、選択、時間切れ、列挙する側の名前 |
| デバッガが宣言どおりに起きること | `21-debug`。偽のデバッガに argv を記録させ、本物の gdb では実際に止める |
| 測ったことと判定したことの区別 | `22-bench`。時間そのものではなく**関係**（min ≤ median）と**形**（数が出る／出ない）を見る |
| 道具に訊いた答が憶えられていること | `23-probe`。`XDG_CACHE_HOME` を木へ向け、shim のコンパイラに別の triple を名乗らせる |

表の後半は、性質ごとに**観測の手立てそのものを設計している**。1行が1つの
技法であり、同じ技法を2つの層で使っていない。`22-bench` の行が「時間ではなく
関係と形」と書いてあるのは、そこが一番の落とし穴だからである——速さは機械と
負荷で変わるので、時間を検査にすると CI と手元で結果が食い違う。

**C から観測できるものは C に書く。** dowel 本体の
`tests/projects/README.md` と同じ規約である。利用者が実際に踏む経路と
同じ形になり、期待値をハーネス側と二重に持たずに済む。

`#error` で書けるのは「届くこと」と「届かないこと」の両方である。
届かないことの検査は、伝播の分離が壊れたときに唯一反応する検査であり、
落としてはならない。

## 4. プロジェクトの構造

```
projects/<name>/
  README.md      何を固定するか
  expect.sh      C から観測できないものだけを書く
  <package>/     dowel.toml を持つディレクトリが1パッケージ
```

パッケージを事例ごとに分けるのは、事例ごとに構成が違う場合である
（`04-diagnostics/cases/`）。変えたいのがマニフェストの中身だけなら、
対象をひとつ置いて差し替える方が、事例の差分がそのまま読める
（`07-robustness/inputs/`）。

`expect.sh` は `.work/<name>/` へ複製された側で走る。実体は変更しない。
実体に `.dowel/` や `compile_commands.json` が現れた場合、`run.sh` が
検出して落とす。ハーネスの経路を通らずに実行した跡だからである。

## 5. 既知の未修正事項の扱い

本体が直っていない事項に対する検査は、消さずに `known_issue` を付けて残す。

```sh
known_issue F-006
ok "the manifest still passes check after applying the suggestion" -C fixed check
```

- 落ちている間は `xfail` として数え、スイート全体は成功のままとする
- 直ると `XPASS` になり、スイートが落ちる。宣言を外す合図である

消してしまうと、直ったことに気づけない。無条件に落としたままにすると、
スイート全体が常に赤くなり、新しい退行が埋もれる。

CI はこの区別をそのまま合否に使う。`fail` と `xpass` のどちらか1件でも
あれば失敗とし、`xfail` は失敗として数えない。publish 用の枝に積む表で見たいのも
各回の合否ではなく、既知の未修正の数が減っていく動きである
（[20-ci.md](20-ci.md) 3節・4節）。

## 6. 規約

### 言語

dowel 本体の規約（`docs/50-development.md` 5節）に合わせる。
**定義と、道具が出力するものは英語。説明は日本語でよい。**

| 対象 | 言語 | 理由 |
|---|---|---|
| 検査名（`ok "..."` に渡す文字列） | **英語** | 本体の Rust のテスト名に相当する。表に並び、CI の要約と publish に出る |
| ハーネスと `run.sh` と `report.py` の出力 | **英語** | 検査名と同じ行に並ぶ。混ざると読みにくい |
| フィクスチャの C（識別子、`#error` の文面） | **英語** | 本体の `tests/projects/` と同じ |
| コード中のコメント | 日本語でよい | 説明である。本体の Rust も日本語 |
| `dowel.build` / `dowel.toml` のコメント | 日本語でよい | 同上。本体の `examples/` も日本語 |
| `README.md` と `docs/` | 日本語 | 説明である |

文書が検査名を引用する場合は、実際の文字列をそのまま書く。
検査名を変えたら引用側も変える。これは `docs` の段が機械的に検査する
（`scripts/check-docs.py`）。実際、検査名を英語へ揃えた際に引用側を
直し忘れ、5件が実在しない名前を指したまま入ってしまった。
文書の不整合はスイートの実行にも影響しないため、検査しない限り検出されない。

### その他

- 検査名は検査内容を書く。`build passes` ではなく
  `private flags of a dependency never reach a dependent` とする。
  失敗した1行だけを見て、何が壊れたか分かる状態にする
- 期待値の根拠を近くのコメントに書く。参照先は dowel 本体の文書番号でよい。
  根拠が書けない検査は、直すべきか期待値を変えるべきかを後から判断できない
- 増分の検査は計数で行う。値が正しいことは、再計算しなかったことを意味しない
- 一時ファイルは `.work/` の下に置く。`/tmp` を使わない

### 観測が dowel の性質かどうかを先に問う

検査を書く前に、**その観測が dowel の性質か、実行した機械の性質か**を
確かめる。機械が答を決める観測は、退行の記録として使えない。CI と手元で
結果が食い違い、どちらが正しいのかを判断する手立てが無くなる。

実際に3度踏んだ。

| 観測 | 実際に決めていたもの |
|---|---|
| 深さ 10000 の入れ子で abort するか | その機械の stack の大きさ |
| 別アーキテクチャの実行ファイルが `Exec format error` になるか | binfmt_misc の登録の有無 |
| `[toolchain] ar = "llvm-ar"` が起動に届くか | `llvm-ar` がその機械に入っているか |

3つ目は道具の**名前**を選び間違えた例である。見たいのは「宣言した名前が
起動に届くか」であって、その名前の実体が在るかどうかではない。ところが
dowel は実在を確かめてから計画するため、無ければ検査ごと落ちる。手元には
`llvm-ar` があり CI のランナーには無く、6件が CI でだけ落ちた。

**道具を名指しする検査は、`run.sh` が始める前に確かめている道具から選ぶ。**
選べないなら、その道具を前提の一覧に足す。環境によって走る検査が変わるのを
避けるという同じ理屈である。

境目の近くを避け、**どの機械でも同じ側に倒れる値**を選ぶ。深さなら
「確実に足りる 64」と「確実に溢れる 100000」の両端だけを使う。
どちらの側にも倒せない観測は、検査にせず所見として記録する。

判定に迷ったら「この検査が落ちたとき、直すのは dowel か、走らせた環境か」
と問う。答が後者なら、それは検査ではない。

## 7. 実アプリの層（`apps/`）

探索の根は2つある。目的が違う。

| | 何を見るか |
|---|---|
| `projects/` | 約束を1つずつ固定する。最小の構成で1点を見る |
| `apps/` | **それらを組み合わせて本物を書けるか**。分野ごとに1つ |

`projects/` の検査は、性質を分離するために構成を最小にする。その分離が
見落とすものがある。**実際の使われ方でしか現れない形**である。

この層が実際に出した所見は、どれも「最小の構成には置く理由が無い」形をして
いる。

| 所見 | 最小の構成では現れない理由 |
|---|---|
| [F-023](10-findings.md#f-023) | 機能名に `/` が入るのはパッケージを跨いだときだけ |
| [F-024](10-findings.md#f-024) | 増分の検査は同じ呼び出しを2回繰り返す。壊れるのは呼び出しの形を変えたとき |
| [F-027](10-findings.md#f-027) | `[toolchain]` と `[runner]` を続けて書くのは、組み込みの構成でしか起きない |
| [F-028](10-findings.md#f-028) | 札を揃えない理由は、ライブラリを配ること——作者と利用者が別人であること——から来る |
| [F-029](10-findings.md#f-029) | 出所を2つ書くのは「切り替えの途中」であり、1回組む検査には現れない |
| [F-030](10-findings.md#f-030) | 自分自身の版を成果物へ埋めるのは、配る側になって初めて生じる |
| [F-031](10-findings.md#f-031) | 同じ書き方が `lib` と `bin` で違う壊れ方をする。分野の違うアプリを2つ書いて初めて並んだ |
| [F-050](10-findings.md#f-050) | 実行ファイルに拡張子が付く対象を選ばないと、名指しする道と書かれる道はずれない |
| [F-051](10-findings.md#f-051) | 族が2つあるという前提は、MSVC を実際に使おうとした側からしか出てこない |
| [F-052](10-findings.md#f-052) | `lib` と `bin` に同じ名前を付けるのは、両方を書く木でしか起きない |
| [F-053](10-findings.md#f-053) | 語彙が足りないことは、足りない語を使いたくなる木を書くまで現れない |
| [F-054](10-findings.md#f-054) / [F-055](10-findings.md#f-055) | **パッケージが分かれていて、かつ triple が複数ある**ときにしか出ない |
| [F-056](10-findings.md#f-056) | 配るライブラリが**自分の検査を持っている**ときにしか出ない |
| [F-057](10-findings.md#f-057) | 下書きを読むだけでなく**実際に組んでみる**まで、`flags` の中身は目に入らない |

F-024 は本スイート自身の見落としでもある。`05-incremental` も `14-scale` も
「同じ呼び出しを2回」の形であり、`test` と `build` を交互に打つという
**実際の流れ**を誰も見ていなかった。

最後の3件は、**新しく入った機構を実アプリに当てて**出た。機構そのものの
フィクスチャは本体の側にあり、そこでは動く。当てる先が実際の木になったとき
だけ、足りない繋ぎ目が見える。

### 書き方

アプリは実際に使えるものにする。動くふりをする骨組みは、組み合わせたときに
何が壊れるかを教えてくれない。

- 走らせて答を見る。組めたことは正しいことを意味しない
- 分離は**破ってみて**確かめる。内部見出しを取り込むと落ちること、まで見る
- 分野ごとに1つ。同じ形を2つ置いても確かめられることは増えない
- **正しい入力だけでは終わらせない。** 壊れた入力で落ちないことまで見る

最後の1つは、`sanitize` という機能フラグとして各アプリに宣言してある。

```
flags      = ["-fsanitize=address,undefined" when feature.sanitize, ...]
link_flags = ["-fsanitize=address,undefined" when feature.sanitize]
```

これは2つを同時に見ている。**アプリ側**——敵対的な入力で落ちないか、未定義
動作を踏まないか、漏らしていないか。そして**dowel 側**——翻訳とリンクの両方に
乗せる必要があり、しかも依存先にも同じものを乗せないと意味が無いフラグを、
マニフェストの語彙だけで書き切れるか。後者が成り立たなければ前者は確かめ
られない。

走らせる先がホストとは限らない。`apps/blink` の対象は基板であり、そこは
`[runner.<triple>]` に qemu を宣言して、**組んだ像を実際に起動する**。
ベアメタルでは、配置が正しいこともベクタ表が生きていることも、走らせて初めて
言える（[F-025](10-findings.md#f-025) の実害はそこに出た）。

GUI も同じである。`apps/plot` は Xvfb を相手にして、**本物の X の伺服体に
繋いで窓を作り、画素を置く**ところまで走らせる。GUI で確かめられないのは
「窓が綺麗か」だけであって、その手前——描いた画素、書き出した像、窓が開いた
こと——はすべて機械にかけられる。境目をどこに引くかが設計であり、それを
支えられるかがビルドツールへの問いになる。

対象が複数あるときは、走らせる先も複数になる。`apps/dsp` は1つの算法を4つの
triple（x86_64 / ARM / RISC-V / Cortex-M）へ組み、**どれでも同じ答が出ること**
を見る。ここで問われるのは組めるかどうかではない。期待値は1枚の見出しに置き、
4つすべてがそれを読む——triple ごとに期待値を分けた瞬間、この検査は「機械が
違えば答も違う」を追認するだけのものになる。

答が同じであることと機械が同じであることは別なので、**機械が本当に違う**こと
も見る。`file` が別の像だと答えること、語長が揃っていて**それが答を揃えて
いる理由ではない**こと。対照を置かないと、全部ホストで組んでいても通る。

ハーネスと記録の形は `projects/` と同じである（1検査1行、`known_issue`）。

## 8. 広げないと決めたもの

| 項目 | 位置づけ |
|---|---|
| VS Code 拡張 | 本体が実物の VS Code で回す E2E を持つ。重ねる意味が薄い |
| クロスの triple をさらに増やす | 機構は同じ。3つ目（RISC-V）を足したのは**クロスを確かめるため**ではなく、「1つの算法が複数の機械で同じ答を出す」を実物にするためだった。4つ目に同じ理由は無い |
| 同じ分野のアプリを2つ | 分野ごとに1つ。同じ形を並べても確かめられることは増えない |

RISC-V の行は、当初「増やしても確かめられることは変わらない」と書いていた。
機構については今もそのとおりである。変わったのは**足す理由**の方で、
`apps/dsp` が要求したのは「クロスがもう1つ」ではなく「同じ答が出る先がもう
1つ」だった。区別しておかないと、次に似た判断をするときに読み違える。
