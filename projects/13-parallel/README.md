# 13-parallel — テストの並列実行

`--test-jobs=<n>` で同時に走らせる。**既定は逐次であり、これは意図した既定**
である。C のテストは共有資源（同じ作業ディレクトリ、固定のポート、書き出し先）
を用いる場合があり、並列を既定にすると順序に依存する失敗が発生する。

## 時間ではなく、テスト自身に観測させる

「並列なら速い」を壁時計で測ると、負荷の高い機械で falsely 落ちる検査になる。
代わりに**同時に居たという事実**を観測する。

各テストは自分の印を `run/<name>.running` として置き、少し待ち、その時点で
見えた印の数を記録し、自分の印を消す。

```
逐次    : 1 1 1 1     （各テストは自分しか見ない）
並列 ×4 : 4 3 2 1     （重なっている）
```

閾値が要らない。単核の機械でも、待っている間は重なる。

## 何を固定するか

### 1. 既定は逐次

`--test-jobs` を渡さないとき、`--test-jobs=1` のとき、いずれも重ならない。
共有資源を持つテストが黙って壊れないための既定であり、
**変わったら知りたい**。

### 2. 並列にすると本当に同時に走る

`--test-jobs=4` と `--test-jobs=2` の双方で重なりが観測できること。
そして**本数は変わらない**こと。取りこぼしは件数に出る。

### 3. 表示は常に要求順

並列にすると終わる順序は入れ替わる。報告まで入れ替わると、実行のたびに
出力が変わり、差分で読めなくなる。逐次と並列で報告の順序が一致することを見る。

### 4. 失敗の扱いが変わらないこと

並列にしたときだけ落ちた回数が変わるなら、どちらの結果を信じてよいのか
分からなくなる。落ちるテストを1つ置いて、件数・終了状態・
`exited with status 3` の表示が逐次と一致することを見る。

`--failed` が並列実行のあとでも効くことも見る。前回の判定は
実行の順序に依らず残る必要がある。

## この形で確かめられないもの

同時に走る本数の上限が `--test-jobs` の値どおりであること。観測できるのは
「重なった」ことであり、`--test-jobs=2` のときに3本目が待たされたかどうかは
外から確実には見えない。競争の結果に依存するため、検査にしていない。
