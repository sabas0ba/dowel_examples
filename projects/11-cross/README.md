# 11-cross — 本物のクロスコンパイル

[06-runner](../06-runner/) は `[runner.<triple>]` の機構を見た。ただし
成果物はホスト向けであり、ランナーは記録を残すシェルスクリプトだった。
qemu も実機も要らない代わりに、**翻訳先が本当に変わったか**は見ていない。

ここでは本物のクロスコンパイラ（`aarch64-linux-gnu-gcc`）で組み、本物の
qemu-user で走らせる。実機は要らないが、翻訳と実行は本物である。

## 答えるのは成果物

`include/arch.h` が `__aarch64__` / `__x86_64__` を見て `ARCH_NAME` を決め、
`sizeof(void *)` からポインタ幅を出す。**名前だけならプリプロセッサの定義で
偽装できるが、ポインタ幅は実体に効く。**

期待値はマニフェストが `cfg.target` から与える。突き合わせは C の中で起きる。

```
defines = { EXPECTED_ARCH = match cfg.target {
    "aarch64-unknown-linux-gnu" => "\"aarch64\"",
    _                           => "\"x86_64\"",
} }
```

アームは**文字列の完全一致**である。`"aarch64-*"` のような形は模様ではなく、
ただの文字列として扱われ、どのトリプルにも一致しない。マニフェスト言語が
文字列埋め込みの小言語を採らないため（本体 `docs/10-manifest.md` 2節）であり、
意図した設計である。

テストは静的リンクにしてある。qemu-user に対象の動的ローダの場所を教える
必要が無くなり、検査が sysroot の置き場所に依存しなくなる。

## 何を固定するか

### 1. 宣言したクロスツールチェーンで本当に組めること

成果物の ELF machine が `AArch64` になること。qemu 経由で走り、
C の側から見たアーキテクチャとポインタ幅が一致すること。

**機構は揃っている。** `[toolchain] c` にクロスコンパイラを書き、
`[runner.<triple>]` に qemu を書けば、組んで走らせるところまで通る。

### 2. 構成がトリプルごとに分かれること

ホストとクロスのビルドディレクトリが両方残ること。片方を組み直しても
もう片方は組み直さないこと。混ざると別の機械向けの成果物を掴む。

### 3. 宣言とトリプルの食い違い

`--target` は構成識別子を変えるが、**ツールチェーンは選ばない**
（[F-015](../../docs/10-findings.md#f-015)）。`[toolchain]` はトリプルごとに
分かれておらず、`[runner.<triple>]` と非対称である。

結果として、ホスト向けの成果物が別アーキテクチャの名前を持つディレクトリに
置かれ、`built:` として報告される。誤りは**起動して初めて**
`Invalid ELF image` として現れる。06-runner が「起動の前に拒む」ことを
約束として見ているのと同じ誤りが、1段あとに戻ってきている。

逆向き（クロスのツールチェーンでホスト向けの構成）も同じ根から起きるが、
**検査にはしていない**。起動できるかどうかが機械の設定で決まるためである。
`qemu-user-static` を入れた環境では binfmt_misc に登録され、別アーキテクチャの
実行ファイルがそのまま起動する。手元では `Exec format error` になり、
CI では通ってしまった。拒まなかった結果が機械によって変わるなら、
その検査が記録するのは dowel ではなく実行した機械である。

## この形で確かめられないもの

実機。qemu-user はシステムコールを翻訳するため、対象機の実際の挙動
（ページ境界、キャッシュ、周辺機器）とは異なる。ここで見るのは
**翻訳先が変わったこと**であり、対象機での正しさではない。

aarch64 以外のアーキテクチャ。機構は同じなので、増やしても
確かめられることは変わらない。
