# 18-tools — ツールチェーンを構成する道具

`[toolchain]` が名指しできる道具は表（`dowel_eval::config::TOOLS`）で決まって
いる。現在は C コンパイラ・C++ コンパイラ・archiver の3つ。

`ar` は [dowel#50](https://github.com/sabas0ba/dowel/issues/50) で足された。
そのとき同時に、道具の集合が表へ集約された。以後この表に1行足せば、宣言も
トリプルごとの選択も実在確認も記録も、既存の機構がそのまま効く。

## 表に載ることで得られる性質

| | 何を意味するか |
|---|---|
| 1. 宣言と既定 | 宣言すればそれが起動される。宣言しなければ既定値 |
| 2. 構成の語彙 | `match tc.<名前>` で具体化を分けられる |
| 3. 実在の確認 | PATH に無ければ `missing-toolchain`。ただし**要るときだけ** |
| 4. 記録された入力 | 差し替えたら作り直す |
| 5. トリプルごと | `[toolchain.<triple>]` で目標ごとに選べる |

`ar` がこの5つを全部持っているかを1つずつ見る。1つでも欠けると、宣言できる
ことの意味が薄れる。

## 5 が組み込みで効く

クロスの構成で archive の作成だけがホストの道具に落ちると、ホストと目標で archive の
形式が違う場合に壊れる。llvm-ar と GNU ar、macOS をホストに ELF へクロスする
場合、ベンダが配る toolchain。**いずれも手元では通り、別の環境で壊れる。**

`cross/` は3つの道具を揃えて宣言し、出来上がった archive の中の目的ファイルを
`readelf` で読んで、本当に目標のアーキテクチャのものであることまで見る。
宣言が届いたことは引数で分かるが、出来上がったものが正しいかは別である。

## 3 の「要るときだけ」

`bin.lone` は archive を作らない。この目標だけを求めるなら、archiver が壊れていても
組めなければならない。C しか書いていない利用者に C++ コンパイラの用意を強いない
のと同じ理屈である。

## 4 の粒度

記録されているのは**道具の名前**であって、その名前が指す実体ではない。同じ
`ar` という名前の裏で別の実体に差し替えても組み直されない。これは `c` も同じで
あり、道具ごとの差ではなく記録の粒度である。そのことを1件の検査として置いて
ある（`the record is the tool's name, ...`）。粒度が変わったときに気づける。

## 中身

| | |
|---|---|
| `host/` | 宣言・既定・要不要・記録。archive を作る目標と作らない目標を持つ |
| `vocab/` | `match tc.ar`。翻訳が `tc.ar` に依存するため `host/` とは分けてある |
| `cross/` | 3つの道具を揃えたクロスの宣言。archive の中身まで見る |
| `typo/` | `ar` の綴り間違い（[F-019](../../docs/10-findings.md#f-019)） |

`vocab/` を分けているのは、翻訳が `tc.ar` を読むと archiver を差し替えたときに
翻訳まで走るのが**正しい挙動**になってしまい、「道具の変更がどこまで波及するか」
を測れなくなるためである。

## まだ無いもの

### 表に無いキーが黙って通る（[F-019](../../docs/10-findings.md#f-019)）

`[toolchain]` の未知のキーは診断されない。綴り間違いはその道具を既定値へ後退
させ、何も言われない。`[runner.<triple>]` と目標のブロックでは `unknown-property`
が出るため、`[toolchain]` だけが外れている。

`typo/` はクロスの宣言で `ar` を `ar_` と打ち間違えた木である。`check` は通り、
aarch64 の archive がホストの `ar` で作られる。#50 が防ごうとした状態が、綴り間違いで
戻る。

### 生成物に対する後処理（[F-020](../../docs/10-findings.md#f-020)）

組み込みでは、リンクの後に必ず1段ある。

| | 例 | 何のため |
|---|---|---|
| 変換 | `objcopy -O binary` / `-O ihex` | 書き込み用のイメージ |
| 変換 | `strip` | 配布用。デバッグ情報つきは手元に残す |
| 検査 | `size` | flash / RAM の予算。**超えたら落ちてほしい** |
| 検査 | `objdump -d` / `readelf -S` / `nm` | 配置と記号を読む |

どちらも表に無く、生成物に対して何かを走らせる場所も無い。
`[runner.<triple>]` は**実行**の側の抽象であり、`dowel test` が組み上がった
実行ファイルを起動するときに通る。生成物から別の形を作る側に対応するものが無い。

dowel の外で objcopy を叩く限り、その道具は記録の外にある。増分にも乗らず、
クロスの宣言も効かない（ホストの objcopy が走る）。

検査は取り込みの構文に依存しない形で置いてある。`tc.objcopy` / `tc.size` が
構成の語彙から引けるかどうかは、実装がどの構文を採っても通る観測である。
生のイメージが出るかどうかを見る1件だけは提案した形を書いており、実装が別の
形を採れば書き換わる。**変換がグラフに乗る**という期待そのものは変わらない。
