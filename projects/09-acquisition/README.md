# 09-acquisition — dowel 自体の取得と版の固定（dowelup）

`dowelup` は dowel を取得し、プロジェクトごとに版を固定し、透過的に
切り替える（[ADR-0013](https://github.com/sabas0ba/dowel/blob/main/docs/adr/0013-self-acquisition.md)）。
`dowel` という名前で起動されると shim として働き、版を選んで exec する。

本スイートにとって、これは**検査対象であると同時に前提でもある**。
「外側から検査する」という立場は、検査する対象が特定できて初めて成り立つ。
その特定を担うのがこの層である。固定が効かないなら、他の全プロジェクトの
結果が何に対するものか分からなくなる。

## 上流に触れずに走らせる

上流は手元の bare リポジトリに差し替える（`DOWELUP_UPSTREAM`）。
`run.sh` が見つけた dowel の作業木を複製し、そこに `main` / `side` / `v0.9.0`
を作る。**ネットワークに触れず、上流の状態にも左右されない。**

`side` と `v0.9.0` は `main` と同じコミットを指す。「同じ sha を別の指定子で
入れる」経路を、取得を増やさずに組み立てられる。実際に組み立てるのは
**1回だけ**で、以降はすべて「すでに入っている」経路を通る。

そのため `run.sh` は dowel のバイナリに加えて `dowelup` と dowel の
**作業木**を要求する。見つからなければ始めない。環境によって走る検査が
変わると、結果を過去の実行と比べられなくなる。

```sh
DOWELUP=/path/to/dowelup DOWEL_SRC=/path/to/dowel ./run.sh
```

## 何を固定するか

### 1. 選択の順序

```
先頭引数の +<指定子>  →  上へ辿って最初の .dowel-version  →  既定
```

上へ辿ること、**近い方が勝つ**こと、`+<指定子>` が pin ファイルより強いこと、
どれも無ければ非零で落ちること。

「見つかった順」と「近い方」は、木の1段目でしか試さないと区別できない。
サブディレクトリにも pin ファイルを置いて分ける。

### 2. 選択はネットワークに触れない

上流を到達不能にしたまま `which` / shim / 取得済みの版への `pin` が通ること。

触れていれば、上流が落ちている日に、**何も変えていないプロジェクトが
ビルドできなくなる**。ADR-0013 がこれを決定として書いている。

### 3. pin ファイル

書かれるのは解決済みの sha だけである。チャネル名やブランチ名を書くと、
選択のたびに解決が要り、2 と両立しない。

| 中身 | 期待 |
|---|---|
| 解決済みの sha | 選ぶ |
| `nightly` / `stable` / `main` / `branch:side` / 短い sha | 拒み、`dowelup pin` を促す |
| 取得していない sha | 拒み、`dowelup install` を促す |
| 大文字の sha、前後の空白、CRLF、末尾改行なし | 選ぶ |
| コメントだけ | 拒む |
| 先頭に UTF-8 BOM | 拒む（[F-011](../../docs/10-findings.md#f-011)） |

**書き方の揺れを受けること**を明示的に見る。`dowelup pin` が書くのが正道
だが、pin ファイルは版管理に入り、人も編集器も触る。

### 4. 指定子の解決

`stable` / `nightly` / `nightly-YYYY-MM-DD` / `X.Y.Z` / `branch:` / `tag:` /
sha のそれぞれについて、解決できる場合と解決できない場合。

**使い方の誤りと、解決できなかったことを終了状態で見分けられること**も見る。
前者は書き直せば直り、後者は上流の状態による。同じ状態で返すと、
自動化した側が再試行すべきかどうかを判断できない。

### 5. 失敗した取得

組み立てに失敗した版が `versions/` に残ると、以後その版を選んだ全ての実行が
壊れたものを使う。**一度きりの失敗が恒久的な状態になる。**

上流に組めないコミットを作って与え、`versions/` に何も残らないこと、
`list` に現れないこと、選べないこと、そして調査のための作業木は
残ることを見る。

### 6. 指定子による選択

`dowelup install <指定子>` が成功したなら、その指定子で選べること。
現在は最初の1つしか記録されない（[F-013](../../docs/10-findings.md#f-013)）。

### 7. release asset からの取得

`stable` / `X.Y.Z` / `tag:` は上流の release asset に置かれた**公開バイナリ**を
取り、隣の `.sha256` と突き合わせる
（[ADR-0036](https://github.com/sabas0ba/dowel/blob/main/docs/adr/0036-prebuilt-distribution.md)）。
それ以外は取るべき asset が無く、cargo で組む。`--from-source` はどの場合も
組む側を選ぶ。

狙いは「**Rust の toolchain が無い機械にも dowel が入る**」ことである。
C/C++ の利用者に、最初のビルドの前に cargo を要求しないための決定であり、
検査もそこを直接見る。

asset の置き場は上流の URL から導かれる。上流を手元の bare リポジトリに
差し替えてあるため、その隣に同じ形の木を置けば、**ネットワークに触れずに
公開バイナリの経路をそのまま通せる**。中身は検査対象の dowel そのものを
入れる。入ったものが動くところまで見たいので、動かない詰め物では代えられない。

cargo を呼ばなかったことは、出力の文言ではなく**痕跡の不在**で見る。
PATH から `cargo` を消すのではなく、呼ばれたら印を残して落ちるものを前に
置き、印が無いことを確かめる。PATH を削ると git などが巻き添えになるうえ、
「呼ばれなかった」ことを直接は見られない。

| asset の状態 | 期待 |
|---|---|
| 在り、`.sha256` が合う | 取る。cargo は呼ばれない |
| checksum が合わない | 拒み、expected と actual を出し、組む側へ退避 |
| `.sha256` が無い | 拒む。検証できないものは取らない |
| `dowel` を含まない | 拒み、組む側へ退避 |
| asset そのものが無い | 組む側へ退避（失敗ではない） |

`.sha256` の書き方も見る。`sha256sum foo.tar.gz > foo.tar.gz.sha256` が最も
自然な作り方であり、それが通らないと**公開する側が黙って踏む**。

残っているのは2件。取得に失敗したときの理由が空で出ること
（[F-060](../../docs/10-findings.md#f-060)）と、入った版が公開バイナリか
自分で組んだものかを後から知る手立てが無いこと
（[F-061](../../docs/10-findings.md#f-061)）。

### 8. 版を名指して取り、中身を確かめる

固定（3節）は「同じ sha が選ばれる」ことしか言わない。**sha が同じでも、
asset の中身が違えば別のものが動く。** ADR-0036 が正直に書いているとおり、
dowel は公開バイナリがその sha から組まれたことを確かめられない。

だから「入ったものが期待どおりか」は、**入ったものに名乗らせる**しかない。
mirror に2つの release を置き、それぞれ別の中身を配る。

| 問い | 見かた |
|---|---|
| 名指した版が来たか | `dowelup run <版> -- --version` に名乗らせる |
| 配ったバイト列が届いたか | 入った実体を、詰めたものと `cmp` する |
| 記録した digest は正しいか | 公開した `.sha256` と突き合わせる |
| 入ったものは働くか | **それで小さな木を組む** |
| 固定した中身が動くか | pin を差し替えて、名乗りが変わることを見る |

最後に**確かめられないこと**も固定してある——dowel でない中身の asset も入る。
限界を検査に書いておかないと、上の検査が言っている以上のことを言っていると
読まれる。由来を要求する手立ては `--from-source` である。

## この形で確かめられないもの

実際の上流に対する解決。`stable` が本当の最新 release タグを指すかどうかは、
上流の状態に依存するため検査にできない。ここで見るのは**解決の規則**であり、
その規則を手元の mirror の上で確かめている。

HTTPS 越しの取得そのもの。asset の経路は `file://` で通しているため、proxy・
TLS・404 の扱いは見ていない。見ているのは**取れた／取れなかったあとの
振る舞い**である。

そして**公開された release そのもの**。ここで見ているのは取得の規則であり、
上流に本当にその形で asset が置かれているかは言えない。それは
[`scripts/check-release.sh`](../../scripts/check-release.sh) の側にある——
`run.sh` の外に置いてあるのは、上流の asset が差し替われば、本リポジトリを何も
変えていないのに結果が動くためである。
