# 10-toolchain — gcc と clang の双方

本体のフィクスチャと CI は `cc` だけを使う。`cc` が何を指すかは機械による
ため、実際に検査されているのは**その機械の既定のコンパイラ1つ**である。

ここで受け持つのは、**宣言したツールチェーンが実際に使われるか**である。
答はマニフェストではなく成果物が持っている。

## 答えるのは成果物

`include/which.h` が `__clang__` / `__GNUC__` を見て `COMPILED_BY` を決める。
成果物を起動すると、自分を翻訳したのがどちらかを名乗る。

```c
#if defined(__clang__)
#  define COMPILED_BY "clang"
#elif defined(__GNUC__)
#  define COMPILED_BY "gcc"
#endif
```

**期待値をハーネスに二重に持たない。** テストの側では、マニフェストが
`tc.c` から与える `EXPECTED` と、コンパイラが与える `COMPILED_BY` を
C の中で突き合わせる。食い違えばテストが落ちる。

```
[test.identity.private]
defines = { EXPECTED = match tc.c { "clang" => "\"clang\"", _ => "\"gcc\"" } }
```

## 何を固定するか

### 1. 宣言が起動に届くこと

`[toolchain] c` に書いた名前がコンパイル行の `argv[0]` に現れること。
ここが `cc` のままなら、宣言は飾りである。

### 2. 成果物が宣言どおりであること

`argv[0]` が正しくても、成果物が正しいとは限らない。起動して名乗らせる。

### 3. `tc.c` による具体化が宣言に追随すること

clang にしか無い警告名（`-Wno-unknown-warning-option`）と gcc にしか無い
警告名（`-Wno-unused-but-set-variable`）を `match tc.c` の両アームに置く。
**取り違えていればビルドが落ちる**ため、引数の一致だけでなく実際に
組めることまで見る。

### 4. ツールチェーンは記録された入力であること

切り替えたら組み直す。組み直さなければ、前のコンパイラが作った成果物が
次のコンパイラの結果として残る。戻したときも組み直す。

同じ宣言のまま組み直せば何も走らないことも見る。切り替えの検出が
「毎回全部組み直す」で実現されていないことの確認である。

### 5. 双方で増分が効くこと

depfile の書式は両者で異なりうる。片方でしか波及を追えないなら、
もう片方の利用者は編集のたびに全部組み直すか、古い成果物を掴む。

実行器は direct で通す。数えるために direct が要るうえ、ninja と direct を
跨ぐと依存の記録が引き継がれない（[F-014](../../docs/10-findings.md#f-014)）。
ここで見たいのはコンパイラの違いであって、実行器の違いではない。

### 6. 実在しないツールチェーン

`missing-toolchain` で、宣言の位置とともに拒む。シェルの `not found` が
利用者に届かないこと（[F-009](../../docs/10-findings.md#f-009) の退行検査）。

## 観測したこと

ビルドディレクトリの名前はツールチェーンを区別しない。`--config` と
`--target` は構成識別子に入るが、`[toolchain] c` は入らない。

正しさの問題ではない。切り替えを検出して組み直しているため、古い成果物を
掴むことはない。ただし gcc と clang を行き来すると毎回組み直しになる。
所見には含めていない。
