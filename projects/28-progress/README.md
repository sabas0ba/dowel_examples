# 28-progress — 同時に走らせ、走っている間に見せる

direct backend は段を同時に走らせ、3つの backend が辺と file の**両方**で
順序を付ける
（[ADR-0056](https://github.com/sabas0ba/dowel/blob/main/docs/adr/0056-direct-backend-parallelism.md)）。
進行は log ではなく出力になった
（[ADR-0057](https://github.com/sabas0ba/dowel/blob/main/docs/adr/0057-progress-is-shown-while-it-runs.md)）。

`dowel build` は `-j, --jobs <n>` を取り、「backend へ渡す並列度」と書かれて
いた。ninja と make は渡していた。**direct はそれを受け取って床に落として
いた。**

その backend は珍しい経路ではない。ninja が PATH に無ければ必ずそこへ落ちる
（ADR-0018）——`dowelup install` の直後の機械がまさにその状態であり、最初の
ビルドに toolchain の組み立てを要らなくするのが dowel の主張である
（ADR-0036）。**その機械へ単線のビルドを渡していた。**

そして同じ機械には、何も出ていなかった。direct は段ごとの告知を `log_info!`
で出しており、既定の log level は `warn` なので誰にも届かない。

## 同時性は、時間ではなく段自身に観測させる

4つの生成が互いに依らない形で置いてある。各段は**走っている間だけ**印を
置き、少し待ち、その時点で見えた印の数を記録して、印を片づける。

| 走り方 | 段が見る印の数 |
|---|---|
| `--jobs 1` | 常に 1 |
| `--jobs 4` | 2 以上 |

壁時計の閾値に頼ると、負荷の高い機械で falsely 落ちる検査になる
（`docs/00-design.md` 6節）。13-parallel がテストの同時性に使っている手を、
そのままビルドの段へ当てたものである。

## 何を確かめるか

| 見るもの | 期待 |
|---|---|
| `--jobs 1` | 段が重ならない |
| `--jobs 4` | 3つの backend すべてで重なる |
| 既定 | 機械の並列度。1本ではない |
| 同時に組んだ結果 | 空から5回組み直して、毎回同じ答を出す |
| 進行の行き先 | stdout ではなく stderr。`dowel graph \| dot` が通ることの約束 |
| log level | `off` だけが黙らせる。既定の `warn` で出る |
| 行の形 | 1段1行、記述が最後。direct は `[n/m]` を付ける |
| 増分 | `m` まで行かない。`m` はビルドの大きさで、予報ではない |

### 走っている間に出ること

元の壊れ方はここだった。`drive` は生成器を `Command::output` で走らせて
いた——プロセスの終了を待ち、捕まえた stdout をそのあとで流し直す。
1.3 秒のビルドの11行が、**最後の19ミリ秒に固まって**出ていた。

検査は段を1つずつ走らせ、行の届いた時刻の開きを見る。4つの生成がそれぞれ
待つので、走りながら出しているなら開き、まとめて流し直しているなら数ミリ秒に
なる。しきい値は遅い機械でも falsely 落ちない側へ大きく寄せてある。

## 順序が片方にしか無いと競合になる

逐次ならどちらか一方の綴りで足りていた。`deps` で整列すれば file の関係も
結果として満たされ、`inputs` の順に走らせれば `deps` も満たされる。
**同時に走らせるとそうはならない。** 片方にしか現れていない順序は競合で
ある。

ninja はもともと `inputs` しか書き出しておらず、file が運ばない辺は既定の
backend では順序ですらなかった。いまは order-only（`|| …`）として書く——
順序を言い、鮮度は言わない。

競合は1度で出るとは限らないので、空から繰り返し組んで見る。
