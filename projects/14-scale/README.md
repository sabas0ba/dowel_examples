# 14-scale — 規模

ここまでのプロジェクトは、どれも数個のソースと数個のターゲットで組んである。
増分の性質はそこでも観測できるが、**増分の費用が木の大きさに比例していない
こと**は、木が小さいと分からない。1つ編集して2つ組み直すのと、1つ編集して
全部組み直すのとが、5ファイルの木では同じに見える。

| | |
|---|---|
| ソース | 120（+ 集計用に1本） |
| 依存する実行ファイル | 8 |
| 依存の連鎖 | 6 段 |
| 総アクション | 138 |

## 木は生成する

リポジトリに 100 を超えるファイルを置くと、差分も一覧も読めなくなる。
中身に意味は無く**数だけが意味を持つ**ため、走らせるたびに
[`generate.py`](generate.py) が作る（[07-robustness](../07-robustness/) が
大きな入力を生成するのと同じ理由）。

## 見るのは時間ではなく件数

`--log-level=debug` は「走らせた数」と「飛ばした数」の両方を出す。

```
ran 0 actions, skipped 138 already up to date
```

**飛ばした数を見ないと、単に知らなかっただけの場合と区別できない。**
0 と報告されるだけなら、全部を考慮したうえで何もしなかったのか、
そもそも 138 個を把握していなかったのかが分からない。

## 何を固定するか

### 1. 費用は変更の大きさに比例する

**規模でしか見えない性質はこれである。**

| 編集したもの | 走るアクション | 飛ばす |
|---|---|---|
| ソース1本（120本中） | 10（そのソース + archive + 依存する8本のリンク） | 128 |
| 依存する実行ファイル1本 | 2（そのソース + そのリンク） | 136 |
| 公開ヘッダ | 138（全部） | 0 |

最後の行が重要である。**「変更の大きさに比例する」は「常に少ない」ことでは
ない。** 公開ヘッダは伝播するのだから、全部組み直すのが正しい。少なく済ませて
いたら、それは取りこぼしである。

### 2. 集合の出入り

ソースを1本足すと新しいものだけをコンパイルし、1本消すと**何もコンパイルせず**
archive とリンクだけをやり直す。

### 3. 波及は宣言ではなく実際の include で決まる

6段の連鎖で、最も深い段の公開ヘッダを編集しても、**それを実際に include して
いる段までしか波及しない**。宣言した依存の深さで決めていると、使っていない段
まで組み直すことになる。

上限も下限も置く。`0 < ran < 全体` を要求することで、「何もしない」（取りこぼし）
と「全部やる」（比例していない）の両方を弾く。

### 4. 大きさに潰れないこと

上限は**非常に緩く**取る。捕まえたいのは機械の速さではなく、木の大きさに対して
二乗以上で効く経路が入り込むことである
（[docs/00-design.md](../../docs/00-design.md) 6節）。

手元では 120 ソースの `check` が 10ms 前後で終わる。**10 秒は 1000 倍の余裕**で
あり、どの機械でも同じ側に倒れる。

## この形で確かめられないもの

計画時間そのものの追跡。`--log-level=debug` に `phase ← plan (1.94ms)` として
出るため読めるが、値を検査にすると機械の速さを記録することになる。
ここで見るのは**内訳が出ること**までである。

実プロジェクトの依存形状（ダイヤモンド、3層以上の伝播、`include/` の相対パス
衝突）。本体の `tests/projects/` が受け持つ領域であり、重ねない。
