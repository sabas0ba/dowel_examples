# 15-cpp — C++

かつて C++ のソースは黙って `cc` に渡され、リンクで
`undefined reference to std::...` になっていた
（[F-008](../../docs/10-findings.md#f-008)）。報告時に挙げた2案のうち、
まず「診断で拒む」（`unsupported-language`）で決着し、その後
**C++ を組めるようにする**側が入った。

**難しいのは翻訳ではなくリンクの側にある。** `.cpp` を `c++` へ渡すだけなら
拡張子を見れば済むが、F-008 の失敗様式は「ソースが `.c` だけの実行ファイルが
C++ に依存する」場合に出る。

## 構成

| | |
|---|---|
| `exts/` | 拡張子1つにつき1本。どちらの driver が選ばれるか |
| `cpplib/` `capp/` | C++ ライブラリと、それを使う**純 C** の実行ファイル |
| `chain/` | `topc[C] → mid[C] → deep[C++]`。推移的な閉包 |
| `reverse/` | C++ の実行ファイルが C のライブラリに依存する |
| `mixed/` | 1つのターゲットに C と C++ が混ざる。増分もここで見る |
| `cross/` | `aarch64-linux-gnu-g++` で組み、qemu-user で走らせる |

## 何を固定するか

### 1. コンパイラはソースごとに拡張子で選ばれる

C++ は `.cc` `.cp` `.cpp` `.cxx` `.c++` `.CPP` `.C`。

**`.C` だけが大文字1文字であり、`.c` と1文字違いで意味が反転する。**
なお大文字小文字だけが違う名前は大小を区別しないファイルシステムで衝突する
ため、ファイル名の語幹は拡張子ごとに変えてある。

### 2. リンクは依存の**閉包**で決まる

`capp/` はソースが `.c` だけだが、C++ のライブラリに依存する。

```
cc    src/main.c        ← 自分のソースは C の driver
c++   src/lib.cpp       ← 依存の側は C++ の driver
link  c++               ← リンクは C++ の driver
```

`chain/` はこれを一段深くする。`topc` は純 C で、依存する `mid` も純 C、
その先の `deep` だけが C++ である。**「直接の依存が C++ なら」で判定して
いる実装は、ここで取りこぼす。**

`reverse/` は向きを変える。C++ の実行ファイルが C のライブラリを使う場合、
「C++ のソースがあるか」だけを見ていると依存の側に引きずられうる。

### 3. 記号が解決するだけでは足りない

引数の形を見るだけでは、実行時が本当に繋がっているか分からない。
`cpplib` は3つの異なる機構を使う。

| | 何が要るか |
|---|---|
| `cpplib_len` | 標準ライブラリ（`std::string`） |
| `cpplib_throws` | **例外の巻き戻し**。記号が揃っていても機構が無ければ abort する |
| `cpplib_ctor_ran` | **書庫の中の大域オブジェクトの構築子**（`.init_array`） |

判定は C の側で行い、終了状態でどれが欠けたかまで分かるようにしてある。

### 4. 1つのターゲットに混在できる

`mixed/` は同じターゲットに `.c` と `.cpp` を持つ。**C の翻訳単位で
`__cplusplus` が定義されていたら拡張子による選択が効いていない**ので、
成果物自身に答えさせる。終了状態に両方の値を載せてあり
（C 側 × 10 + C++ 側）、片方だけが古くても値が変わる。

### 5. 増分は C++ の側でも効く

depfile は driver が出す。C++ の側でも同じように出て、同じように読まれ
なければ、C++ のヘッダを編集しても波及しない。
[05-incremental](../05-incremental/) は C だけを見ているため、この経路は
通っていない。

C だけが読むヘッダと C++ だけが読むヘッダを分けて置き、それぞれの編集が
それぞれの側に届くことを見る。

### 6. ツールチェーン

既定は `c++`。`[toolchain] cxx` で上書きでき、`tc.cxx` で具体化を変えられる。
g++ と clang++ の双方で組め、**C は gcc・C++ は clang++ という組み合わせ**も
通ること。

「C++ のツールチェーンは C++ のソースがあるときだけ要求され、そのときだけ
探される」ことも対で見る。C しか書いていない利用者に C++ コンパイラの用意を
強いるなら、それは C 専用の構成が組めないということである。

### 7. クロス + C++

[11-cross](../11-cross/) は C だけを見る。クロスで C++ を組むと、driver の
選択とトリプルの選択が同時に効く。純 C のテストが別アーキテクチャ向けの
C++ ライブラリを使い、qemu 経由で走るところまで通す。

### 8. 書庫の道具

コンパイラとリンカは宣言できるのに、書庫の作成に使う `ar` は宣言できず、
クロスの構成でも**ここだけがホストの道具に落ちる**
（[F-016](../../docs/10-findings.md#f-016)）。

どの `ar` を使ったかが記録された入力にもなっていない。PATH 上の `ar` を
差し替えても組み直しが起きないため、書庫の中身が黙って変わりうる。

手元と CI の binutils では問題なく通る（総称の `elf64-little` に当たる）。
組み込みのように、ベンダが道具一式を配って混成を想定しない環境で効く。

## この形で確かめられないもの

言語ごとのフラグ（`cxx_flags`、C++ 標準の選択）。本体の実装状況では未決で
あり、今日は `flags` が C と C++ の双方の翻訳単位に適用される。

コンパイラ自身の誤り（構文誤り、テンプレートの誤り）に対する dowel の診断。
C と C++ で挙動は同じであり、どちらもコンパイラの文言がそのまま利用者に
届いて `--message-format=json` には現れない。利用者のコードの誤りに対して
dowel が別の診断を作る筋合いは無く、F-008 が問題にしたのは**構成の誤りが
コンパイラの誤りとして出ること**であって、これとは別である。
