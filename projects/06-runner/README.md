# 06-runner — 実行ラッパ

ホストと異なるトリプル向けに組んだ成果物は、そのままでは起動できない。
`[runner.<triple>]` は起動の仕方を宣言する場所である。

実体として想定されるのは qemu-user、qemu-system、実機への ssh、シリアル経由の
書き込みである。しかし機構そのものは「**成果物のパスを末尾に付けて起動する**」
だけであり、そこに何を置くかは利用者が決める。

そこで本プロジェクトは、記録を残すシェルスクリプトをランナーに置く。
**qemu も実機も要らない**まま、何がどう渡ったかを外から確かめられる。

| パッケージ | 形 |
|---|---|
| `plain` | ランナーを宣言しない |
| `crossed` | `command` と `args` だけ（qemu-user がこれにあたる） |
| `transferred` | `transfer` / `remote_dir` / `host` を伴う（ssh + scp がこれにあたる） |

## 何を固定するか

### 1. 宣言が無ければ起動しない

起動してから `Exec format error` になるのでは、**構成の誤りがテストの失敗として
報告される**。起動の前に `missing-runner` で拒むのが約束である。

拒むのは起動だけである。組むことはできる。

### 2. 渡る引数の形

```
<command> <宣言した args...> <成果物のパス>
```

作業ディレクトリはパッケージルートであり、`command` と `args` に相対パスを
書ける。ビルドディレクトリはトリプルごとに分かれる。混ざると、別の機械向けの
成果物を起動することになる。

### 3. 合否はラッパの終了状態がそのまま返る

握り潰されると、落ちたテストが通ったことになる。テストを `return 3` にして、
`exited with status 3` として報告されることを見る。

### 4. 転送の形（[ADR-0008](https://github.com/sabas0ba/dowel/blob/main/docs/adr/0008-runner-transfer.md)）

対象機がビルド機のファイルシステムを参照できない場合、起動の前に成果物を運ぶ。
**転送元と転送先のパスはマニフェストに書かない。実装が末尾に付け足す。**

```
transfer: <宣言した args...> <ローカルパス> <host>:<remote_dir>/<名前>
command : <宣言した args...> <remote_dir>/<名前>
```

見るのは4点。

1. `transfer` の末尾2つが「ローカルパス」と「転送先」であること
2. `host` が転送先に前置されること（`board.local:remote/remote_test`）
3. 起動コマンドが受け取るのは**転送先のパス**であって、ローカルパスではないこと
4. 成果物が実際に届いていること。届かなければ対象機に古いものが残る

あわせて、**マニフェストにプレースホルダが現れない**ことも記述の側から見る。
`{binary}` のような補間を導入しないという決定は、パス構築を文字列操作として
言語に持ち込まないため（`Path` と `Str` の分離）であり、記法そのものが決定の実体である。

## 実行ラッパの中身

`tools/` のスクリプトは、渡された引数と作業ディレクトリをファイルへ書いてから
本来の起動を行う。標準エラーはテストの出力として捕捉されるため、
ファイルに残さないと外から読めない。

## この形で確かめられないもの

実際のクロスコンパイル（`cc` はホスト向けの成果物を作る）と、
本物の qemu・実機。機構の形は同じでも、`--target` が実際に別アーキテクチャの
コードを吐くようになった段では、この層とは別に確かめる必要がある。
