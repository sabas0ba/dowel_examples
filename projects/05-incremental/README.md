# 05-incremental — 編集してからの再ビルド

```
app ──private──> core
```

`core` はソースを2つ持ち、ヘッダを公開と非公開に分けてある。

| ファイル | 位置づけ | include する側 |
|---|---|---|
| `include/core.h` | 公開 | `scale.c` / `main.c` / 両テスト |
| `src/internal.h` | 非公開 | `offset.c` のみ |

この形にしてあるのは、**波及の範囲を件数で切り分けられるようにする**ためである。
どちらのヘッダを触っても「何かは走る」。走ったものが違うことは、
実行したアクションを数え、どれが走ったかを見て初めて分かる。

## 何を固定するか

ビルドシステムの主要な機能は2回目以降の実行にある。1回の実行を並べても、
編集と再実行を繰り返す経路は検査できない。

### 1. depfile が読めていること

ヘッダの依存はマニフェストに書かれていない。コンパイラが書き出す depfile
からしか分からない。読めていなければ**何も起きず、古い成果物が成功として
報告される**。これは実行時にしか現れない不整合である。

| 触ったもの | 走る | 走ってはならない |
|---|---|---|
| `src/internal.h`（非公開） | `offset.c` | `scale.c` / `main.c` / テスト |
| `include/core.h`（公開） | 全 5 翻訳単位 | — |

非公開ヘッダが依存元へ波及しないことは、**走らなかったこと**でしか観測できない。

### 2. 波及の範囲

- ソースを1つ編集 → その翻訳単位だけ再コンパイルし、下流を作り直す
- 依存元のソースを編集 → 依存側のアーカイブには触らない
- フラグを足す → それを宣言したターゲットの翻訳単位だけ

### 3. 判定の根拠が層で違うこと

| 触ったもの | 走るか | なぜ |
|---|---|---|
| ソースを `touch`（内容同一） | **走る** | 実行器の最新性判定は mtime による |
| `dowel.build` を `touch` | 走らない | 評価は内容で判定する |
| `dowel.build` にコメントだけ追加 | 走らない | 生成されるコマンド列が同じ |

3行目が効いている。マニフェストの中身は変わったが、解決後のコマンドが同じなら
実行しない。判定がファイルの更新時刻ではなく、**そのアクションが何をするか**に
基づいていることを示す。

### 4. 構成をまたいでも壊れないこと

`debug` → `release` → `debug` と往復して、戻った先が最新のままであること。
構成ごとにビルドディレクトリが分かれている以上そうなるはずだが、
記録を共有していると往復のたびに全体が走り直す。

### 5. テストの再実行

`test` ターゲットを2つに分けてある。`dowel test --failed` が「前回落ちた分だけ」を
走らせることは、**走らせなかった件数**でしか観測できない。

1. 両方通る
2. 片方を壊す → `1 passed; 1 failed`、終了状態は 0 以外
3. `--failed` → `0 passed; 1 failed`。通った方は起動すらしない
4. 直して `--failed` → その1件だけ走って通る
5. もう一度 `--failed` → `nothing to rerun`

## 観測の方法

`--executor=direct --log-level=debug` の判定理由を数える。成果物の更新時刻を
見る方法もあるが、時刻の分解能に依存し、「なぜ再実行したか」が記録に残らない。

件数は `runs_actions`、走ったものの識別は `rebuilt` / `not_rebuilt` で見る。

## 実行ファイルの出力

```
scale=6 offset=10
```
