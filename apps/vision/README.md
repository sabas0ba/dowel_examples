# vision — 大きい依存

ここまでのアプリが引いてきたシステムの依存は、cairo と X11 が最大だった
（`-lcairo -lX11` の2つ）。実務で当たるのはそれより一桁大きい。OpenCV の
`.pc` は**リンク旗を 55 個**出す。しかも中身は C++ であり、隣に置く OpenGL
は C である。1つの成果物にその両方が乗り、使う側は C で書かれている。

```
core/   描いて数える。OpenGL（OSMesa）で描画し、OpenCV で解析する。C++
cli/    使う側。C で書いてあり、GL も OpenCV も知らない
```

```console
$ dowel -C core test
$ dowel -C cli build
$ ./vis
size=64x48 bright=962 corner=101418
$ ./vis --blank
size=64x48 bright=0 corner=101418
```

## 旗の量

「全部届くか」だけでは足りない。静的にリンクする木では**並びが解決の順序
そのもの**なので、届いた上で順序が保たれていなければならない。逆に、
重複して届けば同じ書庫を何度も読むことになる。

| | |
|---|---|
| `pkg-config --libs opencv4` が出す `-lopencv_*` | 55 |
| リンクの引数に現れる `-lopencv_*` | 55 |
| 順序 | `diff` で一致（pkg-config が並べた通り） |
| 重複 | 0 |
| 2つ目の依存 | `-lOSMesa` も同じ行に乗る（合計 56） |

`expect.sh` は数を数えるだけでなく、`diff <(pkg-config --libs) <(graph の -l)`
で並びそのものを比べている。数が合っていて順序が崩れる壊れ方は実在し、
それは数えるだけの検査では緑になる。

## 面を保つ

中は C++ で、GL と OpenCV に依存している。使う側は C であり、どちらも
知らない。private な依存は**翻訳には届かず、リンクには届く**。

```console
$ # 使う側の翻訳に渡る -I
/home/user/…/apps/vision/core/include        # これだけ
```

見出しが1枚も漏れていないので、使う側は OpenCV の版が変わっても組み直す
必要が無い。境界は `abi = "c"` で名乗ってある。名乗ってあるから、中が
`c++17` で使う側が `gnu11` でも `abi-mismatch` にならない。

閉包に C++ があるため、**リンクは `c++` のドライバを通る**。使う側が C でも
C++ の実行時が要るが、それを利用者に書かせないのが閉包の仕事である。

## 55 個渡して 2 個要る

リンクの引数と、実行時に本当に要るものは別である。

```console
$ readelf -d vis | grep NEEDED
libOSMesa.so.8
libopencv_imgproc.so.406      # 呼んだのはこの2つだけ
libopencv_core.so.406
libstdc++.so.6                # C++ の実行時。使う側は C なのに要る
libgcc_s.so.1
libc.so.6
```

55 個渡しても、リンカが実際に引くのは呼んだものだけである。`expect.sh` は
`NEEDED` が 20 未満であることを固定している——「渡した数」と「要る数」が
一致してしまったら、それは何かが余計に引っ張られている。

## 表示を持たない機械で GL を走らせる

OSMesa は文脈を作れるので、「窓が開いたか」ではなく**何が描かれたか**を
機械にかけられる。背景は単色で塗るので、隅の画素は厳密に一致する。

| 確かめること | 見るもの |
|---|---|
| 塗れている | 隅が厳密に `VIS_BACKGROUND`（`101418`）である |
| 描けている | 三角形を描くと明るい画素が増え、しかし全部にはならない |
| 隅は無事 | 三角形は隅に届かないので、背景のままである |
| 数えているのが解析の結果 | 閾値を上げると数は**決して増えない** |

最後の1つは「本当に測っているか」を見る検査である。定数を返す実装でも上の
3つは通せるが、これは通せない。

## 計装と `env`

描画も解析も境界の計算だらけなので、`--features=sanitize` で計装し、
無理のある寸法を 10 通り食わせる（`0x0`、`-4x8`、`2000x2`、`zzz` など）。
落ちず、拒むか描くかのどちらかであること。

ここで大きい依存が固有の問題を持ち込む。**下敷きのライブラリ自身が返さない
割り当てがある**。OSMesa は文脈を捨てても内部の表を解放しない。計装されて
いない `.so` の中の話なので、LeakSanitizer からはこちらの漏れと区別が
つかない。

黙らせる先を教える口は環境変数しか無く、それを宣言に書けるのが
`[test.<name>.cases]` の `env` である。

```toml
[test.unit.cases]
triangle = { args = ["triangle"], env = { LSAN_OPTIONS = "suppressions=lsan.supp" } }
```

相対で書けているのは、case の作業ディレクトリが**パッケージの根**だと
約束されているためである。`env` と `cwd` の既定はここで組になって効く。
抑制は `leak:libOSMesa` の1行だけで、こちらの翻訳単位から出た漏れは黙らない。

これが本当に効いているかは、同じ実行ファイルを抑制なしで走らせて確かめて
いる。`LSAN_OPTIONS=suppressions=/dev/null` なら漏れが出る——つまり検知は
生きており、緑なのは `env` が届いたからである。検査がその区別を見ていないと、
「計装した」と書いてあるだけの緑になる。

## 増分

依存が大きいと、組み直しの費用は「触った量」ではなく「触られた翻訳単位」で
決まってほしい。OpenCV の見出しは重く、1つ余計に翻訳すると体感に出る。

`core/src/measure.cc` を触ると、それだけが翻訳され、同じ大きい依存を使う
`render.cc` は組み直されない。使う側はリンクだけやり直す。

## 何を dowel に効かせているか

| | |
|---|---|
| 大きいシステムの依存 | 1つの `.pc` が 55 個の旗を出す。順序も重複も崩さずに届くこと |
| 依存が2つ | GL は C、OpenCV は C++。片方が他方を押し出さない |
| 公開と非公開 | 使う側の翻訳に届く `-I` は1つだけ |
| ABI の境界 | `abi = "c"`。中が C++、使う側が C でも通る |
| リンクのドライバ | 閉包に C++ があればそちら経由になる |
| 言語ごとの標準 | `c_std = "c11"` と `cxx_std = "c++17"` が別々に届く |
| case の `env` | 計装の設定は宣言に書ける。抑制の一覧を相対で指せる |
| case の作業ディレクトリ | パッケージの根であるという約束の上に、上が乗る |
| 実行時の安全 | 計装して 10 通りの無理な寸法を描く |
| 増分 | 隣の翻訳単位が組み直されないこと |
